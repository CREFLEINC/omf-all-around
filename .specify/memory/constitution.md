# OMF MES Constitution

이 문서는 OMF MES(서버 `omf-mes-server`, 클라이언트 `omf-mes-client`)를 Spec Kit 기반
명세 주도 개발(SDD)로 만들 때 모든 작업이 따르는 원칙이다. 통합 저장소 `omf-all-around`에 두고,
명세·계획·작업 목록과 PR 리뷰는 이 문서에 맞는지 확인한다.

## Core Principles

### I. 요구사항 하나가 한 바퀴

- 작업 단위는 **기능 요구사항 1개**다. 요구사항 하나가 `specs/NNN-이름/` 폴더 하나이고,
  명세 → 설계 → 개발 → 검증 → 완료를 한 바퀴 돈다.
- 여러 요구사항을 한 명세에 묶지 않는다. 진행 중에 새 요구사항이 나오면 지금 바퀴에 넣지 않고
  다음 명세 후보로 적어 둔다.
- 한 번에 한 피처를 끝까지 진행한다. 다른 피처는 앞 피처가 완료된 뒤 시작한다.

근거: 단위가 작고 하나여야 명세와 결과를 1:1로 맞춰볼 수 있다.

### II. 명세가 정본이다

- `spec.md`가 그 요구사항의 유일한 정본이다. 계획·작업·코드·테스트는 모두 `spec.md`의 기능
  요구사항(FR)과 완료 기준(SC)으로 거슬러 올라갈 수 있어야 한다.
- 설계팀 설계 저장소(`omf-mes`)의 문서·화면 설계는 레거시다. 명세의 근거로 쓰지 않는다.
  필요한 내용은 `spec.md`에 직접 적는다. API 계약은 원칙 VII을 따른다.
- 명세에는 "무엇을, 왜"만 적고 구현 방법(API 경로, 테이블, 컴포넌트)은 적지 않는다.
  구현 방법은 설계 단계의 `plan.md`에 적는다.
- 개발 중 명세와 다른 동작이 필요해지면 코드를 먼저 바꾸지 않는다. 명세를 고칠 일인지 판단하고,
  명세가 바뀌면 원칙 III의 확인을 다시 받는다.

### III. 설계까지 함께, 그다음은 자율

- **명세 확정**: 사용자가 `spec.md`를 승인해야 확정이다. 확정되는 순간 `omf-all-around`에
  GitHub 이슈를 발행한다. 이슈가 없는 피처는 설계로 넘어가지 않는다.
- **설계 확정**: 사용자가 `plan.md`와 `tasks.md`를 승인해야 확정이다.
- **설계 확정 이후**: 개발 → 검증 → 완료는 Claude가 중간 승인 없이 끝까지 진행한다.
  진행 상황은 이슈 코멘트로 남긴다.
- 예외: 명세나 설계를 바꿔야 하는 일, 데이터 훼손·보안 위험, 되돌리기 어려운 작업(운영 DB,
  배포, 강제 push)은 진행을 멈추고 사용자에게 확인한다.

### IV. 실제 동작으로 검증한다 (NON-NEGOTIABLE)

- 검증은 두 가지를 모두 통과해야 한다.
  1. 변경 범위의 자동 테스트·타입 검사·빌드 통과
  2. `spec.md`의 완료 기준(SC)과 사용자 시나리오를 **실제 앱**(관리웹·POP·모바일 중 해당 채널)에서
     실행해 확인
- 테스트 통과만으로, 또는 API 호출만으로 화면 동작을 대신 확인했다고 하지 않는다. 확인하지 못한
  항목은 미검증으로 남기고 이유를 적는다.
- 검증 결과(시나리오별 통과/실패, 실행 환경, 증거 위치)는 이슈 코멘트로 남긴다.
- 검증할 결과 자체를 테스트 데이터로 미리 넣어 통과시키지 않는다.

### V. 약속은 통합 저장소, 코드는 각 저장소

- `omf-all-around`: `specs/NNN-이름/`(spec·plan·tasks와 부속 문서), 그리고 이슈.
- `plan.md`·`tasks.md`는 서버와 클라이언트 몫을 저장소별 구역으로 나누어 적는다. 작업 경로는
  `omf-mes-server/…`, `omf-mes-client/…`처럼 저장소 이름부터 적는다.
- 구현은 각 제품 저장소에서 피처 브랜치(`NNN-이름`)를 만들어 하고, PR은 저장소마다 따로 올린다.
  모든 PR 본문에 통합 이슈(`CREFLEINC/omf-all-around#번호`)를 연결한다.
- 각 제품 저장소의 기술·도메인 규칙(서버 `CLAUDE.md`의 도메인 규칙·배포 금지 사항, 클라이언트
  `README.md`의 구조·디자인 시스템 규칙)은 계속 지킨다.

### VI. 명세 범위만 만든다

- `spec.md`에 없는 기능, 미리 대비하는 추상화, 범위 밖 정리 작업을 하지 않는다. 발견한 개선점은
  이슈 코멘트에 후속 후보로 남긴다.
- 기존 코드 패턴을 우선 재사용한다. 새 의존성·새 계층이 필요하면 `plan.md`의 Complexity
  Tracking에 이유를 적는다.

### VII. API 계약은 서버 `contracts/` 하나다

- 서버 `omf-mes-server/contracts/*.json`(OpenAPI)이 API 계약의 유일한 정본이다. 서버 개발팀이
  소유하고, 설계 저장소에서 받아오거나 맞추지 않는다.
- 정본은 서버가 실제로 하는 일과 같아야 한다. 계약에 있고 아직 구현되지 않은 오퍼레이션은
  계약 안에 그 상태를 표시한다. 계약과 구현이 다른 채로 두지 않는다.
- 피처가 API를 추가·변경하면, 설계 단계에서 `specs/NNN-이름/contracts/`에 변경안을 쓰고
  설계 승인을 받는다. 구현 단계에서 그 변경을 서버 `contracts/`에 반영하며, 같은 서버 PR에
  구현과 함께 담는다.
- 서버의 계약 기반 장치(타입 생성, 요청 검증, `/api/docs`)는 정본 `contracts/`를 그대로 쓴다.
- 클라이언트의 API 타입과 목 서버는 서버 저장소의 `contracts/`에서 만든다. 어느 서버 커밋의
  계약을 쓰는지 클라이언트에 고정해 둔다.

## 기술 제약

- 서버: NestJS 11 · Prisma 6 · PostgreSQL 16 · pnpm. 마이그레이션은 forward-only.
- 클라이언트: React + TypeScript 모노레포 하나에서 관리웹(브라우저)·POP(Electron)·
  모바일(Capacitor Android)을 만든다. API 타입은 `pnpm contracts:pin` → `pnpm gen:api`로
  서버 계약에서 만든다.
- 현장은 베트남 하노이(UTC+7), 서버·DB 시간대는 UTC 고정.
- 검증용 DB는 로컬 개발 DB만 쓴다. 운영·원격 DB에 쓰지 않는다. `git add .`, `git add -A`,
  강제 push, `migrate reset`, Docker 볼륨 삭제 같은 파괴적 명령은 쓰지 않는다
  (각 저장소 `.claude/settings.local.json` deny 목록).

## 개발 흐름

| 단계 | 명령 | 산출물 | 끝나는 조건 |
|---|---|---|---|
| 명세 | `/speckit-specify` → `/speckit-clarify` | `spec.md` | 사용자 승인 → 이슈 발행 |
| 설계 | `/speckit-plan` → `/speckit-tasks` → `/speckit-analyze` | `plan.md`, `research.md`, `data-model.md`, `contracts/`, `tasks.md` | 사용자 승인 |
| 개발 | `/speckit-implement` | 저장소별 브랜치·커밋·PR (계약 변경 포함) | `tasks.md` 전 항목 완료 |
| 검증 | (원칙 IV) | 이슈 검증 코멘트 | 자동 검사 + 실제 동작 모두 통과 |
| 완료 | — | 검증 보고, PR 병합, 이슈 닫힘 | Claude가 PR을 병합하고 이슈를 닫음 |

- 이슈 제목은 `[NNN] 기능 이름`, 본문에는 요구사항 요약·FR/SC 목록·`spec.md` 링크를 적는다.
- 서버·클라이언트 PR이 함께 있으면 서버 PR을 먼저 병합한다. 클라이언트는 병합된 서버 커밋의
  계약으로 타입을 다시 만든 뒤 병합한다.
- 커밋·브랜치·PR 형식은 각 저장소의 기존 관례를 따른다.

## Governance

- 이 문서는 다른 작업 지침보다 우선한다. 사용자의 최신 지시는 이 문서보다 우선하며, 그 지시가
  계속 적용될 내용이면 이 문서를 개정한다.
- 개정은 `/speckit-constitution`으로 하고 사용자 승인을 받는다. 버전은 semver를 따른다
  (MAJOR: 원칙 삭제·재정의, MINOR: 원칙·섹션 추가, PATCH: 문구 수정).
- 모든 `plan.md`의 Constitution Check와 모든 PR은 원칙 I~VII 준수 여부를 확인한다.
