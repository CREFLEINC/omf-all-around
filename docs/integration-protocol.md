# OMF 파이널 루틴

## 파이널 루틴 운영 규칙

- 사용자 확정(2026-09-12): 새 시나리오를 시작할 때 전용 로컬 테스트 DB를 항상 초기 상태로 되돌리고, 현재 마이그레이션 → 공통 표준/고객 기초 데이터 → 시나리오별 기초 데이터·계정·권한을 적용한다. 테스트에 필요한 데이터와 권한 설정은 승인됐다. 적용 대상은 검증된 전용 OMF 로컬 DB에 한정하며 원격/운영/다른 로컬 DB는 포함하지 않는다. 기존 실행 증거와 초기화 전 백업을 로컬에 보존하고, 입하·검사결과·입고·반품·적치 등 검증할 업무 결과를 시드로 만들어 통과시키지 않는다. 같은 시나리오 중간 재검증은 실행 ID/생성 ID를 이어 사용하며 임의 초기화하지 않는다. 새 전체 실행에 초기화가 필요하면 이전 증거를 보존하고 새 실행 ID를 사용한다.

- 모델은 작업 난도별로 명시적으로 선택한다(사용자 승인된 선택 권한). 시나리오·데이터 흐름 설계 및 어려운 정합 판단: gpt-6-astra / high. 일반 클라이언트·서버 구현과 원인 조사: gpt-5.6-terra / medium. 명확한 절차의 관리자 웹 조작·POP/모바일 API 호출·증거 정리 및 아주 작은 수정: gpt-5.6-luna / low, 화면 판단이 필요하면 medium. Terra에서 해결되지 않는 복합 구현은 gpt-5.6-sol / high 또는 원인·규격 판단이 필요한 경우 Astra로 올린다. 이는 초기 배정 기준이며 실측 비용·실패율을 보며 조정한다.
- 실행 담당은 시나리오 ID/버전, 단계·입력·데이터 변수, 기대 결과, 중단 조건, 캡처 정책을 전달받아 수행한다. 예상과 다르면 실제 결과를 보고하며 임의로 요청·기대 결과·코드를 바꿔 통과시키지 않는다. 정상적인 제품 오류는 모델 실패와 구분해 개발 담당에게 넘긴다. 절차 이해/도구 조작 실패가 반복되거나 새로운 판단이 필요하면 통합 담당이 즉시 더 적합한 모델로 전환한다. 같은 실패를 저렴한 모델로 반복해 시간을 낭비하지 않는다.
- 클라이언트·서버 담당 세션과 역할은 유지한다. 가능하면 같은 세션의 다음 작업에서 모델/추론 수준을 지정하고, 별도 단기 실행 에이전트에는 필요한 지침·시나리오·실행 상태만 전달한다. 부모의 고비용 모델을 무조건 상속하지 않는다. 모델 선택 도구가 없는 환경에서는 바뀌었다고 주장하지 않고 제한을 보고한다. 관리자 웹과 동일 테스트 데이터를 조작하는 실행자는 한 번에 하나만 두며, 실행 중 코드/서버 변경을 피한다.

- 하네스 구성과 운영 절차의 변경은 로컬 전용이다. 이번 하네스 정비의 문서·설정·생성물·bootstrap/검사 코드·관련 테스트 변경을 커밋·PR·원격 push에 포함하지 않는다. 제품 수정 커밋은 파일 또는 hunk를 선별하고 staged diff에서 하네스 변경이 제외됐는지 확인한다. 추적 중인 파일은 .gitignore만으로 보호되지 않으므로 git add . / git add -A로 일괄 스테이징하지 않는다. 통합 관리의 docs/local-harness-files.json을 제외 목록으로 참조한다.
- 스크린샷은 시나리오 첫 실행(initial)과 수정 완료 후 최종 전체 실행(final)에만 보존한다. 해당 실행의 관리자 웹 액션 직전·직후 화면과 실행/캡처 시각·기대/실제 결과를 기록한다. 첫 실행에서 전체 통과하면 그 기록을 최종 증거로 사용하고 재실행하지 않는다. 첫 실행이 중단되면 도달한 단계와 실패 화면까지 보존하고 미실행 단계는 표시한다.
- 중간 수정 검증(recheck)은 실패 구간과 직접 연결된 결과만 확인하며 스크린샷을 보존하지 않는다. 단계·시각·기대/실제 결과·필요한 API/로그 근거만 간단히 기록한다. 수정 완료 후에는 시작부터 끝까지 final을 한 번 실행한다. final에서 실패하면 완료 처리하지 않고 수정 후 다시 최종 실행한다. 기존 증거는 덮어쓰지 않는다.
- 시나리오에 단계별 입력값의 출처, 생성·조회 ID/업무 키, 변경 전후 상태와 기대 값, 다음 소비 단계를 명시한다. 실제 획득한 ID를 실행별 변수표에 기록하고 모든 채널에서 이어서 사용한다. 최종 실행은 동등한 시작 조건과 새 실행 데이터 또는 재사용 조건을 준비한다. 완료된 상태에서 생성·전기 등의 부작용 액션을 무작정 반복하지 않는다.
- 캡처와 단계 기록은 통합 관리의 evidence/<시나리오-ID>/<실행-ID>/에 저장하고, 단계·시도별 before/after 파일을 구분한다. 성공·실패 모두 기록하고 수정 전 실패와 재검증 증거를 덮어쓰지 않는다. 캡처 불가 시 증거 누락과 이유를 명시한다. 화면만으로 저장 성공을 단정하지 않고 필요 시 응답·재조회 결과로 보완한다. 캡처와 테스트 증거도 로컬 전용이며 원격 저장소에 올리지 않는다.

- 이번 계획의 명칭은 파이널 루틴이다. 목적은 남은 개발 기간 안에 클라이언트 동작을 정본으로 서버와의 정합을 빠르게 맞추고 동작하는 프로그램으로 마무리하는 것이다.
- 통합 담당은 시나리오, 기대 결과, 우선순위, 양쪽 수정 범위와 연결 규격을 조정한다. 클라이언트·서버 담당은 같은 담당 세션을 유지하며 배정된 범위의 구현과 관련 검증을 수행한다.
- 이 운영 규칙은 과거 V3 문서의 직접 소통 금지, 사용자 경유 전달, 각 팀의 독자 업무 선택, 전용 팀 번호·GitHub 이슈 선행 의무를 이번 통합 작업에서 대체한다. 과거 문서의 기술·업무 지식은 유지한다. 시스템·개발자 지침과 사용자의 명시적 지시 및 도구 권한은 계속 적용된다.
- 통합 담당과의 작업 메시지로 요청·조사·완료 보고를 주고받는다. 앱의 메시지·상태 조회 도구가 없으면 그 사실과 보고 내용을 현재 세션에 남긴다. 전달했다고 추측하지 않는다. 외부 GitHub 이슈·댓글·메일 발행은 별도 사용자 지시가 있을 때만 한다.
- 제1원칙: 클라이언트 동작이 정본이다. 화면의 입력·액션·요청·표시와 업무 흐름을 먼저 확인하고 서버 API·데이터 처리를 여기에 맞춘다. 기존 서버 계약·DB 모델·설계 문서를 이유로 클라이언트 흐름을 서버 편의에 맞춰 바꾸지 않는다. 클라이언트 자체의 명백한 실행 버그는 흐름을 유지하는 최소 수정으로 해결한다. 클라이언트 동작이 불명확하거나 실제 데이터 훼손·권한 침해처럼 심각한 문제가 확인된 경우에만 해당 지점을 사용자에게 확인하고 독립 작업은 계속한다.
- 제1원칙의 예외(2026-09-14 사용자 확정): 클라이언트 동작 자체에 논리적 모순이 확인되거나 시나리오를 성립시키는 데 필요한 요소가 빠져 있으면, 클라이언트 기능을 수정하거나 추가해 업무 흐름이 자연스럽게 성립하도록 만든다. 정본을 그대로 두고 서버를 억지로 맞추거나, 모순을 남긴 채 시나리오를 통과시키지 않는다. 판단 기준은 서버 편의가 아니라 업무 흐름의 정합이다. 어떤 모순·결핍을 근거로 무엇을 바꿨는지 시나리오와 문제 기록에 남기고, 업무 판단이 갈리는 지점은 사용자에게 확인한 뒤 진행한다. 이 예외를 서버 구현을 줄이려는 이유나 범위 밖 기능 추가의 근거로 쓰지 않는다.
- 제2원칙: 시나리오는 관리자 웹·POP·모바일을 포함한 전체 업무 흐름으로 만든다. 직접 화면 조작 테스트는 관리자 웹에 한정한다. 관리자 웹은 실제 개발 서버에 연결해 입력·클릭·이동하고 결과를 기록하며, API 호출만으로 대체하지 않는다.
- POP·모바일 단계는 해당 클라이언트 코드의 액션·요청 순서·본문·인증/역할·단말 문맥을 확인해 실제 개발 서버 API 호출로 대신한다. 서버가 받기 편한 요청을 임의로 만들어 정합 검증을 통과시키지 않는다. 단계 간 생성 ID와 상태를 이어서 사용하고 이후 관리자 웹 화면에 결과가 반영되는 흐름이면 직접 확인한다.
- 관리자 웹 단계는 initial/final에서 직전·직후 캡처, recheck에서 간단한 실행 기록을 남긴다. POP·모바일 API 대체 단계의 증거는 호출 시각·메서드·경로·비밀값을 제외한 요청/응답·상태 코드·기대/실제 업무 결과다. API 단계에 가상 화면 캡처를 만들지 않는다. 결과에는 관리자 웹 직접 검증과 POP·모바일 API 대체 검증을 구분하고 POP·모바일 UI·실장치 동작은 미검증으로 명시한다.
- 제3원칙: 검증은 일반적인 개발 비용의 평균 수준으로 유지한다. 기본은 해당 시나리오 직접 실행, 실패 구간 재검증, 수정 범위에 필요한 타입/빌드 또는 관련 테스트다. 사소한 수정마다 전체 테스트·전 도메인 회귀·완전한 경계값 탐색·테스트 체계 확장을 반복하지 않는다. 실제 심각한 문제 또는 넓은 영향이 확인될 때만 필요한 범위로 확대한다.
- 시나리오를 막는 오류는 즉시 구현·수정한다. 진행을 막지 않는 경미한 문제는 재현 정보와 함께 기록하고 다음 단계로 진행한다. 발견하지 않은 가상의 문제를 모두 예방하려고 구현을 지연시키지 않는다. 미검증·알려진 결함은 숨기지 않고 최종 결과에 남긴다.
- API 경로·요청·응답·필수값·오류·상태값을 바꿔야 하면 먼저 통합 담당에게 변경안을 전달한다. 통합 담당이 연결 규격을 확정하면 그 범위의 구현을 진행한다. 신규 기능과 범위 밖 개선은 별도 대기 항목으로 기록한다.
- 지시와 기존 지침이 충돌하면 파일·구절·영향을 보고한다. 도구 설정, 플러그인, 스킬을 근거로 다른 업무를 자동 착수하거나 이미 승인된 범위에 반복 승인을 요구하지 않는다.
- 담당은 자신의 저장소를 수정한다. 다른 저장소는 필요한 근거를 읽고 통합 담당에게 수정을 요청한다. 기존 사용자 변경을 보존한다. 이번 로컬 통합에서는 지정된 실제 체크아웃을 사용하며 임의 worktree 생성·브랜치 이동·pull·계약 갱신을 하지 않는다. 커밋·원격 반영·병합은 해당 사용자 지시 범위를 따른다.
- 시나리오 시작 시 통합 담당이 클라이언트·서버·설계 커밋과 미커밋 변경, 계약 버전, 실행 경로를 기록한다. 설계 변경은 차이와 영향 범위를 확인한 뒤 기준을 갱신한다. 기존 계약 고정·생성 검사는 유지하며 실패를 임의로 무시하지 않는다.
- 개발 서버의 경로·명령·주소·프로세스 식별 정보와 재시작 방법을 보고한다. DB는 전용 로컬 개발용임을 확인하고 SQL 파일 경로·체크섬·적용 순서를 기록한다. 기존 DB를 임의 초기화하지 않는다. 비밀번호·접속 비밀값은 보고서에 기록하지 않는다.
- 관리자 웹 검증과 POP·모바일 대체 API 검증은 같은 실제 개발 백엔드의 업무 흐름으로 연결한다. 목 서버나 프런트 단독 테스트 통과를 통합 통과로 보고하지 않는다.
- 문제 보고는 재현 절차, 기대/실제 결과, 관찰 근거, 원인(확정/가설), 해결 방법, 영향 범위로 구성한다. 완료 보고에는 변경 파일, 실제 검증 명령·결과, 재시작 여부, 남은 문제를 포함한다.
- 담당의 구현 완료 후 통합 담당이 실패 단계와 필요한 앞선 흐름을 재실행한다. 공통 기능 변경은 직접 영향받는 대표 기존 시나리오만 추가 확인한다. 미검증과 실패를 통과로 표시하지 않는다.
- 시나리오·결정·문제·실행 증거는 통합 관리 디렉토리에 기록한다. 공개 클라이언트 저장소에는 비공개 설계 본문, 고객 데이터, 화면 캡처, 인프라 비밀정보를 넣지 않는다.

## 상시 필수 코드 검증 (2026-09-13 사용자 확정)

이 규칙은 이번 회차에 한정하지 않고 이후 모든 시나리오에 적용한다. 시나리오 직접 동작 통과와 저장소 필수 코드 검증 통과를 모두 만족해야 완료다.

- 착수 시 양쪽 저장소의 검증 명령과 필수 범위(서버 단위/E2E/타입/빌드 등, 클라이언트 각 앱 테스트/타입/빌드 및 기존 필수 경계 검사)를 확인해 시나리오에 기록한다. CI 비활성화나 명령 미등록을 검증 생략 근거로 삼지 않는다.
- 제품 동작을 추가·수정하면 그 계약과 회귀를 검증하는 기존 테스트·픽스처를 함께 유지한다. 실패는 제품 결함, 테스트 불일치, 환경 문제로 구분하고 원인을 수정한 뒤 재실행한다. 기대값 약화, 무근거 skip, 검사 삭제로 통과시키지 않는다. 제품 회귀 테스트 변경은 제품 변경이며 로컬 하네스 변경과 구분한다.
- 수정 중에는 영향 구간을 집중 검증해 비용을 제한한다. 최종 후보 코드에서는 사전에 정한 양쪽 저장소의 필수 검사를 실행하고 원본 결과를 보존한다. 검증 후 코드가 바뀌면 영향을 받는 검사를 재실행한다. 같은 후보 코드에서 이미 통과한 검사는 근거 없이 반복하지 않는다.
- 서버 E2E는 시나리오 증거 DB와 분리한 전용 로컬 DB에서 실행한다. 최종 증거 DB를 초기화하거나 훼손하지 않는다.
- 검증 전에 실제 Node·패키지 관리자 버전과 CI 선언 버전을 확인·기록한다. CI와 다른 런타임에서 간헐 연결 오류 등 환경 실패가 발생하면 CI와 동일한 버전으로 맞춘 후 재검증한다. 단순 프로세스 생존을 진척으로 판단하지 않고 로그·작업 완료·자원 상태로 장시간 검사의 진행 여부를 확인한다. 중단·실패 로그는 실행별로 보존한다.
- 최종 보고에는 시나리오 동작 판정과 코드 검증 판정을 별도 표시하고, 저장소·커밋/미커밋 상태·실행 명령·범위·통과/실패/미실행 수·로그 경로·수정한 이슈를 기록한다. 필수 검사가 실패·중단·미실행이면 전체 완료로 판정하지 않는다. 사용자 지정 별건(#620 등)은 별도로 추적하되 관련 실패를 숨기거나 통과로 집계하지 않는다.

## 선행 계약 변경 장부 — 모든 후속 작업에 적용 (2026-09-13)

- 기준은 서버 PR #618과 서버 `docs/계약-선행-수정항목.md`의 최신 내용이다. 서버 `contracts/*.json`은 설계 저장소의 읽기 전용 사본이며 개발팀 선행 변경을 직접 적지 않는다. 선행 구현은 서버 코드·명시적 검증·필요한 구현 계약 보정 및 클라이언트 전달본으로 관리한다. 계약 가드가 새 필드·enum·경로를 처리해야 하는 경우에도 사본 직접 수정이나 검증 해제로 우회하지 않고, 원본과 구별되는 명시적 보정 및 회귀 검증으로 해결한다.
- 착수 시 서버 담당은 최신 장부를 읽고 기존 항목과 중복 여부를 확인한다. 클라이언트 담당은 요청·응답·필수값·인증/권한·업무 제약 변경을 서버와 통합 담당에게 전달한다. 서버 담당은 계약보다 앞서는 변경이 생기는 즉시 P-항목을 작성한다. 순수 내부 수정은 해당 없음의 근거를 남긴다. 이미 다른 담당자가 정리한 과거 누락은 다시 등록하거나 되돌리지 않는다.
- P-항목에는 무엇(계약과 다른 필드·동작·제약), 관련 서버/클라이언트/검증/전달본 코드, 왜(사용자 결정·이슈·PR), 다음 계약 갱신 시 같은 내용/미반영/상이한 내용 각각의 처리 방법을 적는다. 번호는 최신 장부에서 중복 없이 정한다. 이 장부는 공유 제품 문서이므로 관련 제품 PR에 포함하며 로컬 하네스 제외 규칙으로 누락시키지 않는다. `docs/coverage-100/계약-사본-당길-때.md`는 마감 기록이므로 새 항목을 추가하지 않는다.
- 커밋·PR 직전 통합 담당은 제품 diff와 P-항목을 대조하고, 담당 완료 보고에 P-ID 또는 해당 없음의 근거가 있는지 확인한다. `contracts/*.json` 변경이 있으면 공식 설계 사본 갱신인지 확인한다. 선행 변경의 직접 수정이나 장부 누락이 있으면 PR을 완료 처리하지 않고 보완한다. 공식 사본 갱신은 출처·설계 SHA와 장부 대조 결과를 기록한다.
- `contracts:update` 전에는 열린 장부와 마감 기록을 함께 읽는다. 같은 내용이 반영되어도 타입·필수 여부·길이 등 제약까지 동등한지 확인한 뒤 중복 가드/전달본 보정을 제거한다. 미반영이면 필요한 검증을 유지한다. 다르게 반영되면 기존 사용자 결정과 클라이언트 영향부터 비교하여 양쪽을 함께 조정한다. 해결한 P-항목은 삭제하지 않고 닫힘 날짜·계약 SHA를 남긴다.
- 갱신 후 계약 생성·타입·계약 unit/E2E 및 영향 업무 검사를 수행한다. 전달본의 SERVER_COMMIT은 main에 남는 실제 커밋을 사용한다. 제품 검사 통과와 설계 반영 완료를 구분하고 보정은 장부와 함께 추적한다.

## 시작과 종료

클라이언트 동작 기준 시나리오·기대 결과 및 필수 코드 검증 범위 확정 → 기준 버전·환경 기록 → 첫 실행·캡처 → 실패 시 제품·테스트 수정 및 집중 재검증 → 수정이 있었다면 최종 전체 동작 실행·캡처 → 같은 최종 후보 코드의 저장소 필수 검증 → 실패 시 원인 수정·영향 검사 및 동작 재검증 → 동작 검증과 코드 검증이 모두 통과하면 결과 보고. 첫 동작 실행에서 전체 통과하면 해당 캡처를 사용한다. 다음 시나리오는 사용자와 정한다.

각 저장소의 통합 지침에는 위 공통 규칙을 동일하게 포함한다. 운영 규칙을 변경하면 세 사본을 함께 갱신하고 클라이언트 어댑터를 재생성한다.

## 모바일 시나리오 검증 순서 — 2026-09-14 사용자 개정

이 절은 모바일을 API 대체만으로 끝내거나 실기기부터 반복 실행하던 이전 순서를 대체한다.

1. 모바일 앱이 구현한 실제 요청 순서·인증·파라미터·응답 처리·저장·다음 화면 진입 조건을 추출한다. 가능한 한 제품 API 클라이언트와 처리 함수를 직접 재사용한다. 별도 수작업 요청으로 앱의 동작을 대신해 통과시키지 않는다.
2. 실제 개발 서버에서 시나리오 순서대로 실행한다. 기대 데이터·상태와 앱의 해석·저장·다음 단계 처리 적합성을 각각 검증한다. 네이티브 저장소 등 대체한 어댑터는 명시하고 실기기 검증으로 과장하지 않는다. 인증 실패 등 시나리오에 필요한 실패 경로도 확인한다.
3. 제품 문제와 관련 회귀를 수정·검증하고 기존 필수 코드 검증을 완료한다. 동일 후보 코드에서 통과한 검사 반복은 피한다.
4. 코드 검증 후 실제 모바일 앱 최종 시연을 수행한다. 관리자 웹의 생성·코드 발급·등록 상태와 모바일 코드 입력·사번·P/O 흐름을 실제 UI로 확인한다. 요청 method/path/status와 비밀 없는 오류 정보를 남겨 코드 검증 결과와 비교한다. 토큰·쿠키·민감 헤더 원문은 기록하지 않는다.
5. 사용자 지정 비용 한도: 최종 실기기에서만 원인을 특정하지 못하는 문제가 지속되면 조사 최대 30분 또는 수정·재검증 2회 중 먼저 도달하는 시점에 멈추고 보고한다. 코드 단계 통과·실기기 실패/미실행·잔여 가설을 구분하며 전체 통과로 보고하지 않는다. 새 기능 구현이나 무제한 장치 조사는 하지 않는다.
